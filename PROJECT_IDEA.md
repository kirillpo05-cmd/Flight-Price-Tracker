# PROJECT_IDEA.md — FareWatch

> **Слой 1 (Документ идеи)** по методологии Spec-First.
> Назначение: исходный документ для AI, из которого генерируется техническая
> спецификация (Слой 2). Пишется по правилу конкретики — числа, таблицы, без абстракций.
>
> **Адаптации методологии под этот проект:**
> - БД — **MongoDB (NoSQL)**, а не Supabase/PostgreSQL. Поэтому «RLS-политики» здесь
>   реализуются как **app-level авторизация** (проверка `user_id == владелец документа`
>   в сервисном слое), а не как декларативные политики Postgres.
> - Проект **намеренно без AI** (демонстрация чисто инженерного бэкенда). По классификатору
>   методологии продакшн-AI-агентов нет → субагент `ai-agent-architect` не создаётся.
> - Статус: **pet/portfolio-проект**. Разделы «Монетизация» и «План запуска» описаны как
>   реалистичная продуктовая модель (для полноты по методологии), но боевая цель — портфолио.

## 1. Проблема

Цена на один и тот же авиамаршрут нестабильна: на типичном европейском направлении
стоимость билета колеблется на **30–60 % в течение 1–2 месяцев** до вылета, а суточные
скачки в ±15–25 % — норма (изменение спроса, динамическое ценообразование авиакомпаний).

Конкретный сценарий боли:
- Студент планирует **RIX → BCN** на гибкие даты в сентябре. «Хорошая» цена — около €90,
  но в среднем по дням он видит €110–180.
- Чтобы поймать €90, он вручную открывает Google Flights **по 10–15 раз** за пару недель,
  в разное время суток, и всё равно может пропустить окно в несколько часов.
- Итог: либо потеря времени (десятки ручных проверок), либо переплата **€40–90** за рейс.

Чего нет в бесплатных инструментах:
- настраиваемых правил («уведоми, если **ниже €100**» / «уведоми при **новом минимуме**» /
  «утренний **дайджест** по моим маршрутам»);
- **истории цен** с графиком (видно ли, что сейчас реально дёшево, или ждать);
- доставки алертов **в Telegram** (а не только пуш в приложении);
- открытого/самохостируемого решения без подписки.

**Боль в одной строке:** поймать низкую цену сейчас = десятки ручных проверок или
переплата €40–90; автоматического, настраиваемого, бесплатного трекера с историей и
Telegram-алертами — нет.

---

## 2. Решение

Сервис, который сам отслеживает цены по правилам пользователя и присылает алерт, когда
выгодно. Процесс пошагово — **каждый шаг становится модулем спецификации:**

1. **Onboarding / Auth** — пользователь регистрируется (email+пароль, JWT), опционально
   привязывает Telegram.
   → *модуль `auth`*
2. **Создание watch** — задаёт маршрут (origin/destination IATA), даты или диапазон,
   пассажиров, класс, и **правило** (порог / новый минимум / процент падения / дайджест).
   → *модуль `watches`*
3. **Планирование** — планировщик периодически (раз в 6–12 ч) ставит в очередь проверку
   каждого активного watch.
   → *модуль `scheduler`*
4. **Опрос провайдера** — воркер запрашивает у источника актуальные предложения, выбирает
   **самое дешёвое**, пишет **снэпшот цены** в историю, обновляет all-time-low.
   → *модули `provider` + `poll-worker`*
5. **Оценка правила** — движок правил проверяет условие; при срабатывании (с учётом
   антиспам-кулдауна) формирует алерт.
   → *модуль `rules-engine`*
6. **Уведомление** — отправка в Telegram и/или email, запись в лог алертов.
   → *модуль `notifier`*
7. **Дашборд** — список watch'ей, график истории цен, текущее лучшее предложение
   (авиакомпания, пересадки, время), лог алертов.
   → *модуль `dashboard`*

## 3. Почему сейчас

- **Amadeus** открыл бесплатный **Self-Service** tier с легальным доступом к Flight Offers —
  раньше реальные цены были только в дорогих B2B-API. Появилась возможность сделать честный
  трекер без скрейпинга.
- Поствосстановление спроса на авиаперелёты → волатильность цен высокая, ценность алертов
  растёт.
- Telegram-боты — привычный и бесплатный канал доставки уведомлений в регионе.
- Конкуренты либо закрыли API (Skyscanner, Kiwi), либо платные (Hopper) — ниша
  «бесплатный, настраиваемый, с историей» свободна.

---

## 4. Целевая аудитория

**Основная:** бюджетные путешественники и студенты, летающие 2–6 раз в год на **гибких
датах**, для кого €50 разницы — значимо.
- Задача: поймать низкую цену, не проверяя руками.
- Текущий инструмент: ручной Google Flights + базовые price-alerts без настройки правил.

**Вторичная:** digital nomads и часто летающие, отслеживающие несколько маршрутов
одновременно.
- Задача: централизованный мониторинг нескольких направлений + история для решения
  «брать сейчас или ждать».
- Текущий инструмент: разрозненные алерты в нескольких приложениях, без единой истории.

### Стек с обоснованием

| Слой | Технология | Почему |
|---|---|---|
| API | FastAPI + Pydantic v2 | Быстрый async, авто-OpenAPI, строгая валидация схем |
| Очереди/расписание | Celery + Celery Beat | Зрелый стандарт для фоновых задач и cron в Python |
| Брокер/кэш | Redis | Один сервис под брокер Celery, кэш последней цены, дедуп алертов |
| БД | MongoDB | Гибкие документы (правила/предложения), time-series под историю цен |
| Auth | JWT + Argon2 | Stateless-токены, безопасный хэш паролей |
| Источник цен | Amadeus Self-Service | Единственный легальный бесплатный реальный источник flight offers |
| Уведомления | Telegram Bot API + SMTP | Бесплатно, привычно; два канала под разные правила |
| Frontend | React + Vite + TS + Recharts + Tailwind | Быстрый дев-цикл, типобезопасность, графики истории |
| Инфра | Docker Compose + GitHub Actions | Мультисервис одной командой, зелёный CI |

### Модули (вход → выход)

| Модуль | Вход | Выход |
|---|---|---|
| `auth` | email, пароль | JWT-токен, запись `users` |
| `watches` | параметры маршрута + правило | документ `watches`, валидация IATA/дат |
| `provider` (FareProvider) | критерии поиска (watch) | нормализованный список предложений |
| `scheduler` (Beat) | расписание (каждые 6–12 ч) | задачи `poll_watch` в очередь (fan-out) |
| `poll-worker` | watch_id | снэпшот в `price_snapshots`, апдейт `lowest_seen` |
| `rules-engine` | watch.rule + текущая/историческая цена | флаг «сработало» + тип алерта |
| `notifier` | user, канал, сообщение | отправка Telegram/email, запись `alerts` |
| `dashboard` (frontend) | JWT, API | экраны: список, график, лог алертов |

## 8. План запуска (фазы, цели, метрики)

### MVP — «работает и задеплоено» *(выделен отдельно)*
Цель: рабочий сквозной поток на одном правиле и реальном деплое.
- Auth (JWT) · CRUD watch'ей · `MockProvider` → затем `AmadeusProvider`.
- Один scheduled-таск опроса + ручной `check-now`.
- Правило **threshold** → алерт в **Telegram** + лог.
- Метрики готовности: сквозной путь «создал watch → пришёл алерт» работает; сервис
  поднимается `docker compose up`; есть живой деплой-URL.

### v2 — «богато»
- История цен + график на дашборде.
- Правила **new_low** и **drop_pct**, **email-дайджесты** по расписанию.
- **Дедуп + кулдаун** алертов; детали лучшего предложения на дашборде.
- Метрики: график строится из ≥7 снэпшотов; повторный алерт не уходит в кулдаун-окне.

### v3 — «полировка/демо»
- Unit + integration тесты, **зелёный CI**.
- Второй провайдер / гибкий диапазон дат (демонстрация абстракции `FareProvider`).
- README со скриншотом/GIF, observability (`/health`, структурные логи).
- Метрики: покрытие движка правил тестами; CI зелёный на каждый push.

## 9. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Лимиты бесплатной квоты Amadeus | Высокая | Кэш последней цены, опрос раз в 6–12 ч, stagger fan-out, retry/backoff |
| Тестовая среда Amadeus = ограниченные/неживые данные | Высокая | `MockProvider` для демо и тестов; в README честно оговорить ограничение |
| Изменение условий доступа к провайдеру | Средняя | Источник за интерфейсом `FareProvider` — замена без переписывания логики |
| Спам алертами (раздражает пользователя) | Средняя | Дедуп + кулдаун на правило, хранение `last_triggered` |
| Низкая доставляемость email | Средняя | Проверенный SMTP (Mailgun/SendGrid), Telegram как основной канал |
| Расползание скоупа (фичи бесконечно) | Высокая | Жёсткая граница MVP; v2/v3 — только после рабочего деплоя |

### Ключевые коллекции (MongoDB)
`users` (email, password_hash, telegram_chat_id) ·
`watches` (origin, destination, dates/range, passengers, cabin, **rule**, active, lowest_seen) ·
`price_snapshots` (**time-series**: timeField=checked_at, metaField=watch_id; price, offer) ·
`alerts` (watch_id, type, triggered_at, price, channel, status).
Индексы: `watches.user_id`, `watches.active`, `price_snapshots{watch_id,checked_at}`,
`alerts.watch_id`. Redis: `lastprice:{watch_id}`, `cooldown:{watch_id}:{rule}`.

### Pipeline обработки (не-AI)
`Beat (cron 6–12ч)` → `fan-out poll_watch(watch_id)` → `FareProvider.search()` →
`выбор min(price)` → `save snapshot + update lowest_seen + cache` →
`rules_engine.evaluate()` → (если сработало и не в кулдауне) → `notifier.send()` →
`запись alerts`.

### Авторизация (вместо RLS)
MongoDB не имеет RLS. Доступ к данным ограничивается в **сервисном слое** `services/authz`:
каждый запрос к `watches`/`alerts`/`price_snapshots` фильтруется по `user_id` из JWT;
любая операция над чужим документом → `403`. Это эквивалент `auth.uid() = user_id` из
методологии, но на уровне приложения.

### Субагенты под этот проект (Слой 4, превью)
По классификатору методологии **продакшн-AI-агентов нет** → `ai-agent-architect` не нужен.
Команда: `database-architect` (Mongo-схема, индексы, time-series) ·
`backend-engineer` (FastAPI, Celery-таски, провайдеры) ·
`frontend-developer` (React-дашборд, графики) ·
`qa-reviewer` (ревью, тесты движка правил, авторизация — **только Read/Bash/Glob/Grep**).
